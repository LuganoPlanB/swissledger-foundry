* TODO [#A] JSON-RPC transport: always emit "params" field                          :P0:
Effort: Medium. Goal: Every JSON-RPC request includes `"params"` (as `[]` when no
arguments) even for zero-parameter methods like `eth_blockNumber`, `eth_chainId`,
`eth_gasPrice`, `eth_maxPriorityFeePerGas`.

Notes:
- The upstream alloy-json-rpc crate (v2.0.1) omits `"params"` when `Params` is a
  ZST (zero-sized type like `()`). It uses `std::mem::size_of::<Params>() != 0`
  in `Request::serialize()` (alloy-json-rpc/src/request.rs:214-236).
- Foundry's provider layer sometimes constructs `Request<()>::new(method, id, ())`
  (ZST, params omitted) and sometimes `Request<Vec<()>>::new(method, id, vec![])`
  (params present as empty array).
- The fix must apply consistently across all RPC transports: MPP HTTP/WS, Curl,
  and RuntimeTransport.
- A runtime config option (`ETH_RPC_REQUIRE_PARAMS=true`) is desirable but not
  mandatory for the MVP.

* TODO [#A] JSON-RPC deserialisation: accept plain-string error responses         :P0:
Effort: Medium. Goal: When the server returns `{"error": "some string"}` instead
of `{"error": {"code": -32600, "message": "Invalid Request"}}`, Foundry wraps
the string into a standard error object instead of crashing with a deserialization
error.

Notes:
- alloy-json-rpc `ErrorPayload` has a custom `Deserialize` impl that expects
  `code` (i64) and `message` (string) fields. A plain string fails.
- The error surfaces as `TransportError::DeserError { err, text }` or
  `RpcError::DeserErr`.
- The fix should intercept the deserialization error, attempt to parse the raw
  response as a plain-string error, and wrap it as `ErrorPayload { code: -32000,
  message: <string> }`.

** TODO [#A] Implement lenient ErrorPayload deserialization
Why: alloy-json-rpc `ErrorPayload` deserialization rejects plain-string errors.
Change: Add a custom deserializer or wrapper that first tries the standard
object format, then falls back to accepting a plain string. Use
`serde_json::Value` as intermediate. Override `RpcError::deser_err` to attempt
re-parsing the raw text as a string and wrapping it.
Tests: Unit test with `{"error": "plain string"}` and
`{"error": {"code": -32000, "message": "msg"}}`.
Done when: Plain-string server errors produce a usable `ErrorPayload` with code
-32000 and the string as message instead of crashing.

* TODO [#B] cast: fix bytes32[] argument parsing                                      :P1:
Effort: Medium. Goal: `cast call <addr> "func(bytes32[])" "[0xAAA..., 0xBBB...]"`
correctly parses and ABI-encodes dynamic bytes32 arrays.

Notes:
- The pipeline: CLI string → `coerce_value("bytes32[]", "[0xAAA...]")` →
  `DynSolType::coerce_str` → winnow parser → `array()` → `fixed_bytes(32)`.
- alloy-dyn-abi's `fixed_bytes(32)` parser requires exactly 64 hex chars. The
  array parser should split on `,` and parse each element independently.
- The errors in FORK.md suggest the parser isn't correctly splitting elements
  inside array brackets, or the hex validation is too strict for comma-separated
  values.
